# Known issues

Known bugs and limitations of the Go backend. New issues are appended with the
next number; the Status column is updated when one is fixed.

Status: `Open`, `Fixed (<version>)`, `Wontfix`.

| # | Description | Status |
|---|-------------|--------|
| 1 | The C runtime cannot PER-encode a present value of `INTEGER (0..18446744073709551615)`: it keeps constraint bounds in a `long`, so even 0 fails ("aper encode failed"). `converter-example` fails identically, and the Go `Encode` returns the same error. Ranges that stay within `long` but exceed 32 bits (e.g. `0..1099511627775`) work. The full signed 64-bit range `INTEGER (-9223372036854775808..9223372036854775807)` has the same problem (its range, 2^64 values, does not fit a `long`): no value can be PER-encoded. | Open (C runtime) |
| 2 | The generated C constraint check for an `INTEGER_t` beyond `long` uses `asn_INTEGER2long`, so values >= 2^63 are rejected ("value too large"); it also triggers a `-Wsign-compare` warning. | Open (C generator) |

| 17 | A `DEFAULT` on a `UTF8String`, `GeneralString`, `GraphicString`, `TeletexString`, `T61String`, `VideotexString`, `ObjectDescriptor`, `UTCTime` or `GeneralizedTime` member was refused: the C generator emitted no default callbacks for these types (the member was always encoded and NULL when absent), and the Go refusal wrongly said that character strings in general have no DEFAULT support.
